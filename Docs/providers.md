# Providers: current state and release plan

Status: design, 2026-10-09 (task 0a5de055, user request #4543). Source refs are to release commit 1909d84 (0.12.3).

## Current state

Providers are `managed = true` entries in `config.toml` (`[agents.<template>]`). `agent_profiles.AgentProfiles.templates` copies them; every team member is a profile on one template. There is no in-app way to add, edit or sign in to a provider.

| Template | Engine (native_adapters / room_runtime) | Sign-in today | Signed-out detection | Model list |
|-|-|-|-|-|
| codex | `codex app-server --stdio` (`native.codex`) | Codex CLI's own ChatGPT login (`~/.codex`) | None before a turn; the turn fails | `cli_catalog`: app-server `model/list` |
| claude | `claude --print --input-format stream-json` (`native.claude`) | Claude CLI's own login | `refresh()` runs `claude auth status`; shows "Run claude auth login in your own terminal" | `cli_catalog`: control `initialize` |
| antigravity | `agy` (`native.antigravity`) | `login_gemini.py`, run by hand in a terminal | Only when the catalog lookup fails (state `blocked`) | `agy models` |
| api (local) | `RoomRuntime.local_turn`: OpenAI-compatible `/chat/completions`, room file and coordination tools | None (no auth header) | `refresh()` GETs `/models` and checks the selected model is served | `/models`, effort from llama.cpp `/props` |

Deliberate guard: `native_adapters.subscription_env()` removes every variable in `API_ENV` (OpenAI, Anthropic, Gemini keys and base URLs, Bedrock/Vertex/Foundry switches, `CLAUDE_CODE_OAUTH_TOKEN`) from provider processes, so a stray key in the user's environment can never switch an agent to paid API billing. It does not change a login stored by the CLI itself: a Claude CLI signed in through the Anthropic Console, or a Codex CLI logged in with an API key, still bills that API account. The status page reports that as `billing: api` instead of promising subscription billing.

CLI discovery (`native_adapters.command`): `PATH`, then known install paths (`~/.codex/packages/standalone/current/bin/codex.exe`, `~/.local/bin/claude.exe`, `%LOCALAPPDATA%/agy/bin/agy.exe`, bundled `providers/antigravity/agy.exe`). Missing CLI raises "official CLI is not installed or discoverable".

## Gaps for a professional release

1. No Setup page: the user cannot see which CLIs are installed, which accounts are signed in, or fix either from the app.
2. Sign-in needs a terminal (`claude auth login`, `codex login`, `python login_gemini.py`).
3. Codex and Antigravity sign-out is found only when a turn or catalog lookup fails.
4. Providers exist only in `config.toml`; adding a local server means editing TOML and restarting.
5. Local models (`local_turn`):
   - Output is capped at `min(2048, max_tokens)`, default 1024, so longer answers are cut.
   - Fixed `temperature` 0.4.
   - No `Authorization` header, so keyed OpenAI-compatible servers (vLLM, LiteLLM, OpenRouter) cannot be used.
   - No context-window awareness: the room prompt budget (`input_chars`, 16000 chars) is the same for a 4k-token local model as for a frontier model.
   - No check that the server returns structured `tool_calls` (llama.cpp needs `--jinja`; Ollama only for tool-capable models). Failure shows at turn time as "returned tool markup as text".
   - No detection of Ollama (11434), LM Studio (1234) or llama.cpp (8080). (S1 added detection, and MLX LM and mlx-serve were added later; see Local model plan.)
6. The CLIs are installed separately by the user; the installer neither bundles nor checks them.

## Auth options

| Option | How | Billing | Fits |
|-|-|-|-|
| A. Subscription sign-in from the app | Setup page runs the official login: `claude auth login --claudeai`, `codex login` (browser), `agy` sign-in. Status from `claude auth status --json`, `codex login status`. Credentials stay in each CLI's own store | Subscription, no API charges | Default for everyone |
| B. API key per provider (opt-in) | Key stored in the OS credential store (Windows Credential Manager, macOS Keychain; Python `keyring`). Passed only to that provider's process: Claude via `ANTHROPIC_API_KEY` env on spawn; Codex via `OPENAI_API_KEY` env or `codex login --with-api-key` (that one writes Codex's global store, so prefer env per process). `subscription_env` stays the default; only a profile explicitly set to API-key mode gets its own key | Paid API usage | Teams without subscriptions; local or remote OpenAI-compatible servers with keys |
| C. Long-lived subscription token | `claude setup-token` (needs a Claude subscription) stored in the credential store and passed as `CLAUDE_CODE_OAUTH_TOKEN` | Subscription | Headless or service installs where a browser sign-in on that machine is not possible |

Not possible: re-implementing vendor OAuth inside ZeroCollab. Subscription credentials belong to the official CLIs.

Recommendation: A for every provider. B as an explicit per-provider opt-in with a visible "API billing" label, never inherited from the environment. C only if headless installs matter.

## Local model plan

- Detection: probe `127.0.0.1:11434` (Ollama `/api/tags`, `/v1/models`), `:1234` (LM Studio `/v1/models`), `:8080` (llama.cpp `/v1/models`, `/props`). Each server kind is a built-in provider with the found models, with no Add step (see "Local servers as providers"); show "not running" with the start command when installed but stopped (`ollama serve`, `lms server start`).
- MLX (macOS on Apple silicon only; other platforms do not list these rows), as built in `provider_setup.LOCAL_SERVERS`:
  - MLX LM (`pip install mlx-lm`, `mlx_lm.server --model <mlx-community/...>`) listens on `127.0.0.1:8080`, the same default as llama.cpp. Its `/v1/models` lists the local Hugging Face cache, and each entry is only `id`/`object`/`created`. Chat completions accept `tools` and return structured `tool_calls` for models whose chat template supports them. Its `--max-tokens` default is 512, but `local_turn` always sends `max_tokens`.
  - mlx-serve (`brew install mlx-serve`, `mlx-serve serve`, needs macOS 26.2+) listens on `127.0.0.1:11234` and serves `/v1/models` and `/v1/chat/completions`.
  - One shared port means one probe, and the port is credited only on positive evidence. `served_by()` recognizes llama.cpp from `owned_by: "llamacpp"`. MLX LM has no marker, and a Python `Server` header or an installed app is not evidence. An identified server shows Running, and the other row shows "<server> is using this port". An answer that names no server becomes a single "Running, not identified" row for that address ("llama.cpp or MLX LM"). Only the identified owner, or that single row, counts as the configured provider at the address.
  - Listing and probing both require Apple silicon (`apple_silicon()`: `platform.machine()`, or `sysctl hw.optional.arm64` for a Python running under Rosetta). Intel Macs, Windows and Linux never probe 11234. Manually configured `api` providers that point at an MLX server elsewhere keep working on any platform.
- Capability check on add: one tiny `/chat/completions` request with a single tool; pass only if the reply carries structured `tool_calls`. Read the context length (Ollama `/api/show` `num_ctx`/model info, llama.cpp `/props` `n_ctx`) and store it.
- Config per local provider: base URL, optional key (credential store), output token limit (raise the 2048 cap; default from context size), context window used to bound the prompt budget for that agent.

## Proposed build slices

| Slice | Delivers | Needs user decision |
|-|-|-|
| S1 | Provider status API and read-only Setup page: CLI installed/version, signed in or not (claude, codex, agy), local servers found | No |
| S2 | Sign in / sign out buttons that launch the official CLI logins and poll status; Codex and Antigravity signed-out detection in `refresh()` | No (subscription only) |

S2 as built (`provider_setup.py`, `Providers.tsx`): `POST /api/runtime/providers/<provider>/sign-in` opens a new console (Windows `CREATE_NEW_CONSOLE`, macOS Terminal through `osascript`, Linux `x-terminal-emulator`/`xterm`; otherwise it returns the command to run) running `python provider_setup.py sign-in <provider>`. That helper runs the official command (`claude auth login`, `codex login`, `agy`) with `subscription_env()` and waits for Enter so the result stays readable. Launches are serialized; a second click while that window is open does not open another on Windows or xterm, where the launched process lives as long as the window. macOS Terminal and terminal wrappers that hand off to a server return at once, so there a repeated click can open another window. The button is held from the click. For providers with a status command (`reports`: Claude, Codex) the page polls every 5 s for up to 3 minutes until the CLI reports signed in, or until the reported method changes for "Change sign-in" on an API-billed login; the deadline is checked on every tick, so failing status requests cannot hold the button. Antigravity has no status command, so it gets a next-step note instead of a wait. Rehearsal previews refuse the route. There is no sign-out button: signing out stays in each CLI. `refresh()` uses the same `sign_in_status`, so a signed-out Claude or Codex agent shows "Sign-in needed" instead of failing its first turn; an unknown answer does not block it. Antigravity signed-out detection remains the model-list check.
| S3 | Providers stored in `data/providers.json` and edited in the app, merged over `config.toml` templates; no restart | No |

S3 as built (`provider_store.py`, `ProviderForm.tsx`, `Providers.tsx`):
- **Store.** `data/providers.json` is `{"providers": {<id>: entry}}`, layered over the managed `config.toml` templates by id. A new id adds a connection. A config id with an entry is "edited", and Reset deletes the entry. `{"removed": true}` hides a config connection until Restore. A file that can't be read is reported on the page and never overwritten; changes stay disabled until it is fixed.
- **Kinds.** Codex, Claude and Antigravity (one connection each, using the official CLI and its own sign-in), and `api` for OpenAI-compatible servers. So an install whose `config.toml` has an empty `[agents]` can still connect subscriptions.
- **Fields.** Name and color for every connection. For a server, also the address (http or https, no user name, password, query or fragment), the model, and the maximum response length (256 to 32768 tokens). `local_turn` now sends that value instead of capping it at 2048.
- **Checks on save.** Creating a connection, or changing a server's address or model, lists that connection's models with exactly those settings first. The model must be served. Ids are fixed: a rename edits only the label, and `status` and `probe` are reserved.
- **Guards.** Changes are refused in a rehearsal preview, while a deployment check blocks writes, and during a repository change. Edit, Remove and Reset are refused while an agent on that connection is mid-turn, so a turn's config is never changed under it. Idle agents get the new template at once. Remove is refused while any agent uses the connection in any saved project, archived agents included.
- **First agent.** A connection no agent uses keeps its own model list (from save and from Refresh connections), so Add agent offers it, and the first agent's model is checked against that list. No agent is created automatically.
- **Routes.** `GET /api/runtime/providers`, `POST /api/runtime/providers` (create), `POST /api/runtime/providers/probe` (a server's models, nothing saved), `POST /api/runtime/providers/<id>` (edit), and `.../<id>/remove` and `.../<id>/reset`.
- **Not in S3.** The structured tool-call check, the context window and API keys. Those are S4 and S5.
| S4 | Local provider detection, capability probe, key header, output and context limits | No |

S4 as built (`provider_setup.tool_call_check` and `server_context`, `provider_store`, `room_runtime.local_input_budget`). The key header is deferred to S5.
- **Tool-call check.** Saving a local connection (new, or with a changed address or model) sends one `/chat/completions` request with a single `report_ready` tool, to exactly that address and model.
  - It goes the way a real turn does: streamed, with the connection's `request_options`, assembled by `room_runtime.stream_chat` (the same code local turns use) and judged by `local_protocol.visible_text` and `validate_calls`.
  - A server that handles tools only without streaming therefore fails the check, instead of passing it and failing every turn.
  - It passes only on a valid structured `report_ready` call.
  - Tool markup returned as text fails, with the fix named (llama.cpp `--jinja`, or a tool-capable model).
  - A failed check refuses the save.
  - The result is stored on the entry (`tool_check`) with its address and model. Changing either clears it.
  - `POST /api/runtime/providers/check` runs the same check without saving, behind the same gates.
- **Context window.** Read from the server's own reports, in this order:
  1. `/v1/models` `max_model_len` or `context_length`;
  2. llama.cpp `/props` `n_ctx`;
  3. LM Studio `/api/v0/models/<id>`;
  4. Ollama `/api/ps` for a loaded model, then a Modelfile `num_ctx`.
  It is labelled approximate with its source. A number entered in the form is labelled "entered by you" and kept when the address changes.
  - The tool-call check runs first, so an Ollama model is usually loaded and reported by `/api/ps`.
  - If no window is reported and none is entered, the save is refused. An unknown window isn't safe: Ollama silently drops the start of an over-long prompt, which removes the room instructions.
- **Prompt budget.** For a local agent with a known window: (window - maximum response length - instructions and tool definitions - 256) x 3 characters. That counts the 14 tools, about 9.2k characters, and this agent's instructions. The room prompt uses the smaller of this and the project's input limit.
  - A window too small for this refuses the save, or fails the turn with a clear message.
  - Every tool round is budgeted, not only the first request. Tool results (file tools and the room's own tools alike) are capped at 16,000 characters. With a known window, each result is cut to an equal share of what is left after the response and everything already in the conversation, with a note on how to read a smaller range.
  - After each request the characters-per-token estimate is recalibrated from the server's reported `usage.prompt_tokens`, bounded to 1.5 to 4 characters per token.
  - Local connections saved before S4 (no window, no check) keep the standard budget, protected only by the 16k result cap, until they are edited and saved again, which runs the check.
  - The check sends the connection's own maximum response length. A reply cut off by that length is reported as such, with the fix, not as a model that cannot call tools.
  - When almost nothing is left, results are replaced with a short "window is full" note so the model can still answer. When nothing at all is left, the turn stops with a clear message.
  - With today's instructions and tools, 8k-token windows are too small, and about 12k tokens or more are needed.
  - Characters per token is an estimate, so the budget is approximate, not a hard bound.

Local servers as providers (task 6b673b03, contract `local-providers/contract.md` r1; `provider_store`, `provider_setup.local_status`, `AgentProfiles.describe`):
- **Built-ins.** Each `LOCAL_SERVERS` kind this computer can run is a provider with a fixed id: `local-ollama`, `local-llamacpp`, `local-lmstudio`, and on Apple silicon `local-mlx` and `local-mlxserve`. The same id is `profile.template`, `/profiles` `providers[].id` and `/providers/status` `local_servers[].template`. Named connections can't take a `local-` id, and Edit, Remove and Reset refuse built-ins. A new named connection at a built-in's address is refused while that built-in runs there as itself; a server there that the probe can't identify is used as a named connection.
- **Status.** `running`, `stopped`, `not_installed`, `port_taken` or `unidentified` (the shared :8080 answer names neither llama.cpp nor MLX LM), and `unknown` until the first probe after start. Only `running` is offered. Status comes from the last `GET /providers/status` (Team calls it on opening and on Refresh connections); there is no polling loop. When a probe finds a server started, stopped or advertising different models since the previous one, it runs the full refresh, so the models in the agent editor and the blocked state of its agents follow at once.
- **Models.** The catalog is what the server advertises on `/v1/models`. The first time a (provider, model) pair is chosen, the S4 tool-call check and context read run for that model, and the result is cached per model in providers.json. A new choice on a provider that isn't running is refused with `{error, field}`. Unchanged provider and model never re-check, so a stopped agent stays editable.
- **Stopped provider.** Its agents keep their provider and model and show blocked, with the start command. They are never moved to another provider.
- **Migration.** Once, recorded as `migrations: ["local-providers-1"]` in providers.json: a no-key `api` connection at a local default address (today `bonsai` at :8080) becomes that built-in. Agents in every project keep their id and history and get the built-in plus the old model (`Bonsai-2-27B`). The connection's settings become per-model settings, the old connection is hidden with `{removed: true}`, and one chat note announces it. If any project's agents.json can't be read, the whole migration waits for the next start. The built-in entry is written as a complete `api` connection, so the previous release still runs those agents.
| S5 | API-key mode (option B) with the OS credential store | Yes: enable paid API keys at all |

S5 design (user answer d14490f5: yes, as an option; not shown anywhere until a valid key is entered; an on/off switch per API provider; a cost tracker). Security pre-build review 44578130 applies. Mockup: `/uploads/2dfb0c33.png` on task 0a5de055.
- **Agents never hold a key.** A room-side relay (`provider_relay.py`, mounted at `/relay/<connection>/...` on the room port) adds the key and forwards only to that connection's fixed vendor origin (`https://api.anthropic.com`, `https://api.openai.com`). The CLI gets the relay address plus a relay token minted for that run, valid only while the run is active, the same lifetime as the run token in 85653a8e.
  - Claude Code: `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>/relay/<id>` and `ANTHROPIC_API_KEY=<relay token>`, set after `subscription_env()` strips the user's own variables.
  - Codex: a `model_providers.zerocollab_relay` entry passed with `-c` (base URL `.../relay/<id>/v1`, `env_key` naming a variable that holds the relay token, `wire_api = "responses"`), selected with `model_provider`. This never touches Codex's own login store.
  - The relay accepts only its own token for that connection, strips incoming auth headers, streams the response through unchanged, and never logs headers or bodies.
  - Honest limit: agents run as the user, so an agent that sets out to read Windows Credential Manager can. The relay keeps the key out of agent environments, tool subprocesses, chat, commits and logs in normal work. During its turn, an agent could spend through the relay with its relay token, bounded by the monthly limit.
- **Key storage.** OS credential store only: Windows Credential Manager (`win32cred`, already in the venv), macOS Keychain (`security`, key passed on stdin, never argv), Linux Secret Service (`secret-tool`, stdin). One entry per connection, named `ZeroCollab/provider/<id>`, holding the key and the origin (scheme, host, port) it is for. A connection's origin is fixed by its kind, and for an `api` server, changing the address through the app deletes the key. Keys with whitespace or control characters are refused before storing.
  - **Origin checked on every send** (security f72d5e0b A). providers.json can be edited by any same-user process, so every path that attaches a key (`local_turn`, the `refresh()` model list and check-and-save) compares the connection's current origin with the stored one. On a mismatch no key is sent and the turn fails with "The address for <name> changed outside the app; enter its API key again in Team > Providers."
  - **No redirects or environment proxies** for keyed calls (`follow_redirects=False`, `trust_env=False`, as the existing clients already do), so a redirect or an `HTTPS_PROXY` never receives the key.
  - A plain `http://` origin that is not loopback gets a warning before saving: the key would cross the network unencrypted.
- **Human-only, write-only.** Set, replace, delete and settings go through UI-token routes only: `GET /api/runtime/providers/keys`, `POST /api/runtime/providers/keys` (check and save), `POST .../keys/<id>` (on/off, limit, prices), `POST .../keys/<id>/delete`. Run tokens are already refused there. GET returns presence and the last 4 characters at most, and no route ever returns a key. Honest limit: the UI token is in the public `/` page (`run.py`), so a same-user process that sets out to can still turn a key off, replace it or delete it; it still can't read one back through the room. The key is never in providers.json, config.toml, events, logs, stderr echoes, exports, deploy packages or backups. Removing a connection deletes its credential.
- **Valid before visible.** Check and save lists the models with the key (free). For an `api` server it then runs the S4 tool-call check with the key, which is one small billed request (a few hundred tokens); the form says so. Only a key that passes is saved. API connections appear in Add agent, Connect and the team builder only with a valid key and the switch on. Valid but switched-off connections stay listed on the Providers page so they can be turned back on.
- **On/off switch per connection.** Off keeps the key and refuses new requests. A request already running completes; the next request in that turn (a tool round) is refused and the turn ends with "API provider turned off". Agents on it show "API provider turned off" with a link to Team > Providers and don't start, and Add agent hides it. An agent is never moved to a subscription or another connection.
- **Cost tracker.** Each keyed response's token usage is appended as `{connection, agent, run, model, input, cached, output, time}` to `data/api_usage.jsonl`, with no content. For `api` servers `local_turn` records it from the response `usage`; in S5b the relay does the same for Anthropic (`message_start`/`message_delta`) and OpenAI (`response.completed`). Cost = tokens x per-model prices per million (input, cached input, output). Prices are entered per connection in S5a; S5b adds a built-in table for Anthropic and OpenAI with its as-of date and source. A model with no price, or a response with no usage, shows "unavailable", never $0. A day or month total that includes such a response shows the known part as "at least $X", with a note naming what is missing (design c08c8a70). The panel shows today, this month and a per-agent breakdown, labelled "Estimated cost" and "Tokens"; the provider's bill is authoritative.
- **Spend stop (S5c).** An optional "Monthly spending limit (USD, estimated)" per connection; blank means no limit. At or over it, new requests are refused and the turn fails with "Monthly API limit reached for <name> ($X). Raise it in Team > Providers." A request already running completes, so the total can go over the limit by that response; the field says so. Built: see "S5c as built".
- **Keyed OpenAI-compatible servers** (`api` kind, for example OpenRouter or vLLM): the room makes these calls itself (`local_turn`), so the key goes into the room's own `Authorization` header. No relay is needed and no agent sees it. The same storage, origin binding, switch and metering apply.
- **Panel states** (design 7ffdae51, mockup on task 0a5de055).
  - No keys: below Local models, only an "Add an API key" button and one line saying keys are optional and billed by the provider. The Subscriptions text mentions API keys only once one is saved.
  - Add: focus moves to the first field. Fields are name, server address, API key (masked) and, after the check, the model and an optional context window (blank reads it from the server). "Check and save" announces "Checking key" and can't be pressed twice. Errors are tied to their field and announced: "Key not accepted by <host>. Key not saved; check it and try again." or "Couldn't reach <host>. Key not saved." with Retry. No raw server response is shown. Cancel clears the key field and returns focus to the button that opened the form; a successful save or a changed address also clears it.
  - Saved: "Key ending ...a1B2", "Saved keys can't be shown. To replace one, enter a new key." Replace uses the same form; a failed replacement says "Replacement not saved; the previous key is still in use" and leaves the key and switch unchanged.
  - Switch: a keyboard switch named "Use <name> API", with its on/off state announced.
- **Slices.** S5a: key store, routes, the panel, keyed `api` servers, usage recording and the cost view with per-connection prices. Only `api` rows are offered (security f72d5e0b C); Anthropic and OpenAI keys wait for S5b, since nothing would use them yet. S5b: relay, Claude and Codex wiring, relay metering, built-in prices; relay path allowlist per vendor, constant-time token check and a Host check on `/relay`. S5c: spend stop. Each is reviewed separately. Checks use dummy keys and a stub vendor only; no real key is used by agents.

S5a as built (`provider_keys.py`, `provider_store.py` key routes, `ApiKeys.tsx`; `room_runtime.local_turn` and `refresh`):
- **Store.** `provider_keys.save/load/delete`. On Windows it calls advapi32 `CredWriteW`/`CredReadW`/`CredDeleteW` through ctypes, so there is no new dependency. On macOS it uses `security -i` with the command on stdin, and on Linux `secret-tool` with the secret on stdin. The entry is `ZeroCollab/provider/<id>@<8 hex of the data folder>` and holds base64 of `{key, origin}`. Keys must be 8 to 512 printable ASCII characters with no whitespace, quotes or backslash. Only the Windows path has been run; macOS and Linux are unverified.
- **providers.json** keeps `key_target` (the connection id), `key_hint` (the last 4 characters), `enabled` and `prices`, never the key. A key connection keeps its server: an edit that changes the origin is refused ("add a new API key"), rather than deleting the key. Removing the connection deletes its entry. As in S3, Remove is refused while any agent, archived ones included, uses it.
- **Routes** (UI token):
  - `POST /api/runtime/providers/keys/probe` takes `{base_url, key}` and returns the models (free); it warns on non-loopback http.
  - `POST /api/runtime/providers/keys` is Check and save: the model list, then the S4 tool-call check and context read, all with the key; it stores the key, then saves. It takes an optional `context_tokens`. An entered window too small for the room is refused before the billed tool call. A blank window the server can't report still costs that one call, because it loads the model first (Ollama reports a loaded model's context).
  - Refusals that belong to one field carry it: the JSON error has `field` = `key`, `model` or `context_tokens` (`provider_store.FieldError`, read as `ApiError.field`). The add form shows the message under that field and marks only that field invalid, so a missing context window never makes an accepted key look wrong; a context refusal also moves focus to the context field. An unnamed refusal is shown for the whole form. Draft values are kept, and Check and save is the explicit retry.
  - `POST /api/runtime/providers/keys/<id>` takes `{key?, enabled?, prices?}`. A replacement key is checked first, and a failure says "Replacement not saved; the previous key is still in use" and changes nothing.
  - Editing an API key connection in the existing form loads models and runs Check with its saved key (`id` in the body).
- **Every keyed request** goes through `provider_keys.headers(cfg)`: the model lookup, the status probe, `refresh()`, and each `local_turn` round, set after the tool-schema fetch. It refuses with a message when the connection is off ("API provider turned off: <name>"), when the key is missing, or when the address no longer matches the stored origin. Errors from the server are reduced to "Key not accepted by <host>", "Couldn't reach <host>" or "<host> answered HTTP n"; the reply body is never shown.
- **Usage.** `local_turn` appends one row per keyed request, after `stream_chat`, with input = prompt - cached, cached, and output. A response without usage is written as `missing`. A request that fails mid-stream is not recorded, which is a known gap. The summary covers today, this month and per agent. A missing price or missing usage makes a total "at least $X" with a note naming what is missing, and an amount below a cent shows "<$0.01". A blank cached-input price is charged at the input price.
- **Off.** Add agent hides the connection (`offered: false` from `/api/runtime/profiles`), and creating an agent on it is refused. Duplicating an agent on it starts the copy on the first offered provider; only editing the existing agent still shows the off connection. `refresh()` marks its agents blocked with the off message, and their cards link to Providers.
